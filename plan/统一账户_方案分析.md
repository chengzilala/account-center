# 统一账户中心 — 方案分析

> **状态**：分析稿（未进入开发）
> **日期**：2026-10-23
> **适用**：个人官网 `personal-site` + 微信悦读（H5 / 插件 / 小程序）+ 未来作品
> **文档位置**：已迁入独立项目 `account-center/plan/`（2026-10-23，项目骨架建立后）。
> **⚠️ 结论已变更（2026-10-25）**：本文关于「首期复用微信悦读 CloudBase 环境 / 用 CloudBase 静态托管 / CloudBase 邮箱验证码」的结论**作废**。最终方案为**与奶茶项目同台腾讯云轻量服务器**（Node 常驻 + Nginx/Caddy + HTTPS + 单机 JSON 存储 + 自建 SMTP）。以下内容仅作设计取舍的历史依据保留，口径以 [RPD_需求文档.md](RPD_需求文档.md) v0.3 为准。

## 0. 一句话结论

**账户中心单独做一个项目 `account-center`；代码独立，首期运行复用微信悦读现有的 CloudBase 环境，页面走独立子域 `account.chesterlee.cn`；个人官网只放“登录 / 我的”入口，不承载账户逻辑。**

一句话记忆：**代码独立成项目，环境先借用，域名保持中立。**

## 2. 现状盘点（按代码核对）

| 作品 | 形态 | 现在的身份 / 登录 | 数据在哪 | 主要问题 |
|---|---|---|---|---|
| 个人官网 [works.html](file:///Users/Admin/Knowledge/Coding/personal-site/web/works.html) | 纯静态，腾讯云轻量 | 无登录 | 无 | 无法显示“我的作品 / 已开通”状态 |
| 微信悦读 | 插件 + H5 + 小程序 | **账户码**（32 位本机随机串，账号=凭证） | 微信云开发 | 身份绑在本机；换设备靠抄码 / 6 位码；没有邮箱，无法跨产品认人 |
| 高驰跑步看板 | CloudBase 网页 | **邮箱验证码**，可设密码 | CloudBase | 又一套账号；和微信悦读互不相识 |
| 公众号 | 站内文章 | 无登录 | — | 不涉及 |
| 寻光（未来可能挂） | 自建 Node | **手机号 + 密码**，Bearer Token 7 天 | 自建服务器 | 第三套账号；再挂新作品就是第四套 |

**结论：不是“缺一个登录页”，而是缺一个统一的身份层。** 现在每加一个作品，就多一套注册、登录、找回、退出、隐私和后台。

## 3. 先把三件容易混的事分开

这是设计统一账户最关键的一步：

| 层 | 是什么 | 归谁管 |
|---|---|---|
| **平台账号** | “你是 Chester 网站的用户，uid=xxx” | **账户中心统一管** |
| **第三方授权** | 高驰 OAuth、微信读书 Key、DeepSeek Key | **各作品自己管**，账户中心最多显示“已连接 / 未连接” |
| **业务数据** | 跑步数据、阅读人格、书架、笔记 | **各作品自己管**，用 uid 关联 |

统一账户不等于把所有数据搬到一个库。账户中心只解决“你是谁、能进哪个作品”，第三方 Key 和业务数据继续留在原作品里，这样风险最小，迁移也最轻。

## 4. 目标模型

```
官网 / 各作品
      │  点“登录” → 跳转
      ▼
┌─────────────────────────┐
│ 账户中心                 │
│ uid / 邮箱 / 登录方式     │
│ 作品清单 / 开通状态       │
│ 我的设备 / 退出全部 / 注销 │
└─────────────────────────┘
      │  一次性授权码（5 分钟、只能用一次）
      ▼
作品 A          作品 B          作品 C
(自己的数据)    (自己的数据)    (自己的数据)
```

生活类比：账户中心是**一张身份证 + 一张门禁卡**，作品是不同店铺。身份证只证明“你是你”，店铺里买过什么、存了什么，仍归各店。

### 核心规则

1. **一个 uid 走天下**：所有作品只认 uid，不存密码、不存邮箱（可存展示用昵称）。
2. **登录方式可以多，账号只有一个**：邮箱验证码、旧账户码、小程序 openid，最终都映射到同一个 uid。
3. **官网不掺业务**：官网保持纯静态，只加“登录 / 我的”入口，不接数据库、不引 SDK。
4. **旧账户不强制搬家**：老用户第一次登录时“绑定旧身份”，数据不丢、旧入口保留一段时间。
5. **先做“能登录、能识别、能授权”**，首期不做付费、不做复杂角色。

## 5. 账户中心放哪里：方案对比

| 放法 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **A. 独立项目 `account-center`** | 边界清晰、可复用、独立发版、未来作品都接它 | 多一个项目要维护；要配域名和部署 | **推荐** |
| **B. 放进 `personal-site`** | 官网现成、入口近 | 官网是**纯静态 + 腾讯云轻量静态目录**，跑不了云函数；接 CloudBase 会破坏“零构建、零依赖”；两套部署链 | **只放入口，不放账户逻辑** |
| **C. 放进 `微信读书插件`** | 复用现有 CloudBase、账户码、`wre_users`、openid 绑定，最快 | 账户中心变成微信悦读的附属；未来作品要依赖“微信读书插件”这个仓库；发版、权限、隐私都纠缠 | **可作临时落脚，不作长期方案** |
| **D. 只在 CloudBase 控制台写云函数** | 不用建项目 | 没有本地代码、不能回滚、不能协作、不能测试 | **不推荐** |
| **E. 新开一个 CloudBase 环境** | 隔离最干净 | 小程序跨环境、旧数据迁移、成本都更复杂 | **第二阶段再考虑** |

**结论：A + 首期复用现有环境**，也就是“代码独立、环境借用”。这比纯 C 干净，比纯 E 省事。

## 6. 推荐的最终形态（三层）

```
代码层    account-center/               独立项目、独立仓库、独立版本
运行层    微信悦读现有 CloudBase 环境     先复用：新建 ac_* 集合 + accountCenter 云函数
访问层    account.chesterlee.cn          登录页 / 我的账户 / 管理页 + API
```

“复用环境”不等于“寄人篱下”：

- 账户中心只用**自己的集合** `ac_*`，不改 `wre_*`；
- 只新增一个云函数 `accountCenter`，不动 `wereadProxy` 的既有 action；
- 两边通过**明确的接口契约**通信；
- 以后要独立环境，把 `ac_*` 导出、换个 env id 即可，作品侧只认 API 域名，不用改。

## 9. 数据模型（建议）

| 集合 | 关键字段 | 说明 |
|---|---|---|
| `ac_users` | `uid`、`nickname`、`avatar`、`status`、`createdAt` | 人的主档 |
| `ac_identities` | `_id`（如 `email:xx` / `device:xx` / `wx:xx`）、`uid`、`createdAt`、`lastUsedAt` | 一把钥匙一行，全部指向 uid |
| `ac_sessions` | `sid`、`uid`、`appId`、`deviceId`、`refreshHash`、`expiresAt`、`revoked`、`ip`、`ua` | 登录会话 |
| `ac_login_codes` | `code`、`uid`、`expiresAt`、`used`、`attempts` | 6 位临时登录码 |
| `ac_products` | `appId`、`name`、`url`、`status`、`createdAt` | 作品清单 |
| `ac_entitlements` | `uid`、`appId`、`status`、`expiresAt` | 首期全部默认 `active` |
| `ac_audit_logs` | `actorUid`、`action`、`target`、`ip`、`createdAt` | 登录、绑定、退出、删除等 |

> `wre_users` / `wre_sync` / `wre_links` **保持不动**。账户中心只读它来识别老账户，不把微信读书 Key 搬进 `ac_*`。

## 10. 身份模型：uid 是“人”，其他都是“钥匙”

这是“账户码 + 邮箱两种方式合一”的关键：

| 标识 | 代表什么 | 用途 |
|---|---|---|
| **uid** | 一个人 | 全局唯一，所有作品只认它 |
| **email** | 一把跨设备钥匙 | 邮箱验证码登录、找回 |
| **deviceId** | 一把设备钥匙 | 微信悦读现有账户码，继续可用 |
| **openid** | 微信小程序钥匙 | 小程序内静默识别 |
| **6 位码** | 临时钥匙 | 跨设备登录，10 分钟、一次性 |

多个标识都指向同一个 uid。例如：

1. 用户先用微信悦读，有 deviceId；
2. 后来在账户中心用邮箱登录，系统把 `deviceId → uid` 绑上；
3. 以后用邮箱、账户码、6 位码登录，都进同一个 uid；
4. 小程序 openid 也绑到同一个 uid。

**这样老用户零迁移，新用户也不用被迫记住 32 位码。**

### 登录流程（MVP）

| 方式 | 流程 |
|---|---|
| **邮箱验证码** | 输入邮箱 → 收 6 位码 → 验证 → 查/建 `email:<邮箱>` → 得到 uid → 建会话 |
| **账户码** | 粘贴 32 位账户码 → 校验存在 → 查/建 `device:<账户码>` → 得到 uid → 建会话（严格限流，视同密码） |
| **6 位码** | 已登录设备生成 6 位码 → 另一台输入 → 换回 uid 并建会话（10 分钟、一次性） |
| **小程序 openid** | 云函数从调用上下文取 openid → 查/建 `wx:<openid>` → 得到 uid；如已有 deviceId，一并绑定 |

### 绑定规则

- 一个 uid 可以有多把钥匙；
- 一把钥匙只能属于一个 uid；
- 绑定前若发现冲突，提示“这个账户已属于另一个账号”，由用户确认是否合并（首期可只提示、不自动合并）；
- 解绑只解除当前钥匙，不删除 uid 和其他钥匙。

## 11. 接口契约（MVP）

| 接口 | 作用 |
|---|---|
| `POST /auth/email/send` | 给邮箱发验证码 |
| `POST /auth/email/verify` | 验码登录 / 注册 |
| `POST /auth/account-code/login` | 用账户码登录 |
| `POST /auth/code/start` | 生成 6 位临时登录码 |
| `POST /auth/code/redeem` | 用 6 位码登录 |
| `GET /me` | 当前 uid、昵称、邮箱掩码 |
| `GET /me/products` | 我的作品及状态 |
| `POST /auth/logout` | 退出当前设备 |
| `POST /auth/logout-all` | 退出全部设备 |
| `POST /account/delete` | 注销账户（二次确认） |
| `GET /admin/users` | 管理后台：用户列表 |
| `POST /admin/revoke` | 管理后台：强制下线 |

> 实际实现放在一个云函数 `accountCenter` 里，用 `action` 字段路由，和微信悦读 `wereadProxy` 的风格保持一致。

## 12. 与现有作品怎么接

| 作品 | 接法 | 改动量 |
|---|---|---|
| **微信悦读 H5** | 账户中心登录后确认 / 返回本机 deviceId；H5 继续用原来的 `wre_*` 接口 | 小，加一个“登录 / 账户”入口即可 |
| **微信悦读插件** | 插件“账户与多端同步”增加“邮箱登录统一账户”；拿到 deviceId 后仍存 `wreAccount.id` | 小，现有同步逻辑不动 |
| **微信悦读小程序** | 云函数天然有 openid；用一次性绑定码把 `openid → uid` 绑上 | 中，复用现有 `wre_links` 思路 |
| **个人官网** | 顶部加“登录 / 我的”；作品卡不加复杂状态（首期规则是“登录即可用”） | 很小，只加链接 |
| **高驰看板** | 以后再做：邮箱 / 旧 uid → 统一 uid | 暂不动 |
| **未来作品** | 引入 `ps-auth.js`，调 `/me` 和 `/me/products` | 新作品接入成本低 |

### 微信悦读的关键兼容策略

- `wre_users._id` 继续用 `deviceId`，**不迁移、不改主键**；
- 账户中心只新增 `device:<deviceId> → uid` 的映射；
- H5 / 插件继续按 deviceId 读写原数据，行为不变；
- 老用户第一次在账户中心用邮箱登录时，把当前 deviceId 绑到 uid；
- 新用户从账户中心登录后，账户中心分配一个 deviceId 给微信悦读，H5 照常保存。

这样首期不需要改微信悦读的核心数据模型，风险最低。

## 13. 运行环境：复用 vs 新开

| | 复用微信悦读环境（首期） | 新开独立环境 |
|---|---|---|
| 迁移旧账户 | 可直接读 `wre_users`，绑定 deviceId 很容易 | 要跨环境导出 / 接口，麻烦 |
| 小程序 | 同一个 env，云函数直接调 | 小程序跨环境更复杂 |
| 成本 | 不增加环境费用 | 多一个环境 |
| 隔离 | 靠 `ac_*` + 独立云函数 + 接口契约 | 最干净 |
| 风险 | 微信悦读环境变更会牵连账户中心 | 运维更重 |

**建议：首期复用；等账户中心稳定、或第二个非微信悦读作品正式接入时，再迁独立环境。**

迁移触发条件（满足任一即可）：

1. 账户中心需要独立计费 / 独立配额；
2. 微信悦读环境要做大改，可能影响账户中心；
3. 接入第二个非微信悦读作品，且跨环境调用变复杂；
4. 你需要更严格的权限隔离。

## 14. 部署前置条件

1. **CloudBase 邮箱验证码**：确认现有环境能开通邮件登录 / 配置发件通道；不行就接腾讯云邮件推送。
2. **域名**：`account.chesterlee.cn`，需要 DNS、HTTPS、备案（主域名已在用，通常问题不大）。
3. **静态托管**：账户中心页面放 CloudBase 静态托管，尽量和 API 同域，省掉 CORS。
4. **密钥**：Token 密钥、邮件密钥只放云函数环境变量，不进代码仓库。
5. **备份**：`ac_*` 集合定期导出；审计日志保留一段时间。
6. **管理员**：第一个 admin uid 手动写进配置，不走注册。

## 15. 落地顺序与验收

| 阶段 | 做什么 | 验收 |
|---|---|---|
| **0. 定契约** | 写《统一账户规范》+《接入契约》：uid、登录、令牌、作品、数据归属 | 你确认后所有作品按同一份契约做 |
| **1. 账户中心 MVP** | 邮箱验证码 + 账户码 + 6 位码登录；我的账户；我的作品；退出 / 退出全部 / 注销 | 一个邮箱和一个 deviceId 能落到同一 uid |
| **2. 官网入口** | 顶部“登录 / 我的”；作品卡先保持“登录即可用” | 从官网能进账户中心并返回 |
| **3. 微信悦读 H5/插件** | 账户中心返回 / 确认 deviceId；原有 `wre_*` 接口不改 | 老用户绑定后数据不丢；插件同步照常 |
| **4. 微信悦读小程序** | openid → uid 绑定；复用 `wre_links` | 小程序和网页同一 uid |
| **5. 以后** | 独立 CloudBase 环境、高驰接入、未来作品 SDK、授权 / 付费 | 新作品只接一次 |

## 16. 主要风险

| 风险 | 应对 |
|---|---|
| 复用环境导致耦合 | `ac_*` 独立集合 + 独立云函数 + 接口契约；随时可导出迁移 |
| 账户码等于密码 | 强制 HTTPS、限流、失败锁定、6 位码一次性短时有效 |
| 邮件进垃圾箱 | 用 CloudBase / 腾讯云正规发件通道，提供重发和换邮箱 |
| 小程序 openid 绑定 | 个人小程序不能用 web-view，继续用一次性绑定码 |
| 跨域登录态 | 不用共享 Cookie；用 5 分钟一次性票据换作品侧会话 Token |
| 旧数据迁移 | 惰性迁移：首次登录才绑，不批量搬；保留旧入口一段时间 |
| 官网被“动态化” | 官网只加链接，不接 CloudBase SDK，保持纯静态 |
| 同一把钥匙绑到两个 uid | 绑定前查冲突；首期只提示，不自动合并 |

## 17. 明确不做（首期）

- 不把各作品的数据库合并成一个。
- 不自研整套 OIDC / 加密体系，先用平台能力 + 一次性授权码。
- 不强制老用户改密码 / 重新注册。
- 不把账户中心塞进静态官网，官网保持“零构建、零依赖”。
